## 0. How this review was done

### 0.1 Clean-room compliance

I followed `CONTRIBUTING.md` and `docs/spec/README.md`:

- I used only public documentation (URLs in §1). I downloaded, ran, and
  inspected no Plex binary, decompiled code, leaked source, or client app.
- I copied no Plex text into the repository beyond short setting and
  endpoint *names* needed to identify features, and short quotations with
  citations.
- Plex's official OpenAPI document was downloaded into `/tmp` as untrusted
  data. I parsed it with an isolated Python script (`python3 -I`) only to
  list operation names and parameters. Nothing from it was committed. The
  document is published under the Apache-2.0 licence (stated in its
  `info.license`).
- One throwaway Go test, `internal/library/zz_review_probe_test.go`, called
  `ParseMovie` on four file names (finding F-15). I deleted it right
  after, and `git status` was clean again.
- I ran no broad `go vet` or `go test -race`; the parent runs those.

### 0.2 What I inspected

- **Code:** every route registration in `internal/server`, and the
  config, entrypoint, library store/scanner/apply/collections,
  play-state store, auth middleware, login limiter, decision endpoint,
  atomic file writer, and GDM.
- **Specs:** all 14 pages under `docs/spec/`.
- **Delivery:** CI (`.github/workflows/ci.yml`), the `Dockerfile`,
  `deploy/compose*.yaml`, the container smoke test, the e2e harness, and
  the release notes.

I treated the README's status checkmarks as claims to verify, not as
evidence.

### 0.3 Classification vocabulary

| Class | Meaning |
|---|---|
| **Missing** | No implementation and no spec |
| **Partial** | Some behaviour exists; documented Plex behaviour is absent or differs |
| **Implemented-but-unverified** | Code and spec exist, but nothing shows it works with real clients, hardware, or Plex-shaped traffic |
| **Intentional divergence** | Deliberately different from Plex, marked **(sloplex)** or stated by policy |
| **External-service-dependent** | Plex provides this through plex.tv or other Plex cloud services. Full parity would need that service, or a local replacement that clients would also have to accept |
| **Defect** | Current behaviour is wrong or unsafe on its own terms, whatever parity says |

Priorities:

- **P0:** data loss or security exposure in features that already ship.
- **P1:** blocks compatibility with real clients or the parity goal.
- **P2:** a major feature gap.
- **P3:** completeness or polish.

## 2. Executive summary

At this commit Sloplex is a careful, well-tested **movie and TV server**
that speaks a Plex-*shaped* HTTP API. It has local accounts, a built-in web
app, and a strong ffmpeg transcoding pipeline. It is **not close** to a
complete reimplementation of Plex Media Server:

- It registers about **75 routes** (`internal/server/*.go`). The official
  public API alone documents **207 paths**, about 300 operations (S1), and
  is itself incomplete (S2).
- Whole product areas are absent:
  - music, photos, and other-video libraries;
  - DVR and Live TV;
  - play queues, hubs, sessions, and events;
  - the preferences API and runtime settings;
  - library management over the API;
  - media analysis: markers, chapters, preview thumbnails, loudness;
  - extras;
  - downloads and optimised versions;
  - scheduled maintenance and backups;
  - DLNA.
- The settings that do exist are a static JSON file read at startup
  (`internal/config/config.go:25-67`). There is no `/:/prefs`.
- Several endpoints Sloplex does implement **differ in HTTP verb or path**
  from Plex's official documentation, so a client written against that
  documentation fails (F-10).
- **No artifact shows that any real Plex client works with Sloplex.** There
  are no recorded fixtures, no client matrix, and no target Plex version.
  The tests check Sloplex against its own spec (F-11).
- The spec's provenance sections cite "publicly available community
  documentation" with **no URLs, versions, or dates**. A clean-room auditor
  cannot trace any fact to its source. The official Apache-2.0 OpenAPI
  document from 2025-09 is never cited (F-09).
- **The scope conflict that matters most:** the policy "Sloplex does not
  contact plex.tv" (`CONTRIBUTING.md:21`, `docs/spec/README.md:27-30`) is
  incompatible with full parity for official Plex apps. Those apps sign in
  and find servers through plex.tv, and S1's own auth model issues PMS
  tokens from plex.tv. I report this as a scope decision for the owner and
  do not override it (§3).

## 3. Scope conflict: "no plex.tv" versus "complete reimplementation"

**This is reported, not resolved.** The rules state:

- `CONTRIBUTING.md:21-22`: "Sloplex does not contact plex.tv or any other
  hosted service. Pull requests that add such calls will not be accepted."
- `docs/spec/README.md:27-30`: identity, accounts, and tokens are local.
  The only outbound connections are GitHub and the owner's own TrueNAS.
- `README.md:9`: "It never contacts plex.tv or any other hosted service."

The public documentation shows these Plex features depend on Plex cloud
services:

| Plex capability | Dependency per public docs | Consequence under current policy |
|---|---|---|
| Official Plex apps signing in and listing servers | S1 "Authenticating with Plex": PIN and JWT flows at `clients.plex.tv/api/v2/*`; `GET https://clients.plex.tv/api/v2/resources` lists servers and per-server `accessToken`s | Official apps that require a plex.tv sign-in **cannot reach Sloplex as documented**. Only clients that accept a direct URL plus token could work, and none were tested (F-11) |
| Claiming a server (S4) | plex.tv account | Not possible. Sloplex uses a local owner account instead (intentional divergence) |
| Remote access via UPnP/NAT-PMP plus plex.tv publication, Relay, custom server access URLs (S6, S9) | plex.tv | Replaced by Tailscale (`deploy/compose.tailscale.yaml`) as an intentional divergence |
| Secure connections with `*.plex.direct` certificates (S1 path base; S6) | Plex certificate service | No TLS at all today (F-07). A local custom certificate *is* server-local and possible |
| Friends, sharing, Plex Home, managed users, and Plex Pass gating | plex.tv | Only local accounts. Per-library restriction exists; sharing does not |
| Online metadata agents, marker source "online", lyrics, sonic data | Plex metadata services | Sloplex reads local `.nfo` only (intentional divergence, `docs/spec/metadata.md:371-372`) |
| Push notifications (S4), webhooks (S6) | Push uses Plex services. Webhooks are outbound to a URL the user chooses | Push: external. Webhooks could be local, but the "any other hosted service" wording in `CONTRIBUTING.md:21` makes even user-configured webhooks ambiguous |
| EPG for Live TV (S1 EPG group) | Plex guide service | External. A local XMLTV alternative would be an intentional divergence |

**Decision the owner needs to make (no recommendation is implied by parity alone):**

- **(a)** Keep the policy and redefine the goal as server-local parity
  for third-party or direct-connect clients. Every row above then becomes
  an intentional divergence, and the README should stop implying full
  Plex-app compatibility.
- **(b)** Allow optional, off-by-default plex.tv integration under a
  documented exception, as was done for GitHub and TrueNAS.
- **(c)** Build local substitutes, such as a local resources/PIN service,
  and accept that official apps will not use them unless those apps can
  be pointed at a custom endpoint. I found no public documentation that
  they can.

There is also an internal inconsistency to fix whatever is decided:

- `README.md:9` and `CONTRIBUTING.md:21` say "never ... any other hosted
  service".
- `updateCheck` defaults to `true` (`internal/config/config.go:91`) and
  calls `api.github.com` (`docs/spec/updates.md:240-241`).

`docs/spec/README.md:27-30` admits the exception; the other two documents
do not. This is F-27.

## 4. Findings

Each finding lists its evidence, user impact, the missing behaviour, and
acceptance criteria. Line numbers are at commit `5808f4e`.

### P0: data safety

#### F-01 · P0 · Defect: an empty or partly unreadable library root silently deletes library items

**Evidence**
- `internal/library/scanner.go:136-141`: the only guard is that each root
  exists and is a directory. An unmounted mountpoint is an existing,
  empty directory, so it passes.
- `internal/library/scanner.go:155`: an unreadable *subdirectory* is
  logged ("skipping unreadable path") and skipped. Its files are then
  missing from the result.
- `internal/library/store.go:467-489`: `ApplyScan` rebuilds the section
  from the files found. Anything not found is removed (`apply.go:44-52`).
- `internal/library/apply.go:77-100`: IDs are reused only for a file path
  seen in the previous scan. Files that come back after a removing scan
  get **new** IDs.
- `internal/library/collections.go:241-245`: manual collection members not
  present in that scan are deleted from the collection permanently.
- `docs/spec/playlists.md:160-165`: a playlist entry for an item that gets
  a new ID "stays hidden".
- Play state is keyed by item ID (`internal/playstate/playstate.go:27`), so
  history is orphaned.
- The spec promises protection only for a *missing* root
  (`docs/spec/http-api.md:305-307`, "This keeps an unmounted drive from
  wiping the library"). For the most common unmount case that promise is
  untrue in practice: the mountpoint directory still exists.

**User impact.** A NAS share that is not yet mounted at boot, an NFS
hiccup, or a permissions change on one folder causes these, with nothing
but log lines to warn the user:

- the library is emptied or partly emptied;
- every account's watch history and resume points become detached;
- manual collections lose members;
- playlist entries vanish.

Plex instead keeps missing items in the library, flagged unavailable,
until the trash is emptied. "Empty trash automatically after every scan"
is an explicit opt-in that Plex warns about (S5, S13).

**Missing behaviour.**

- Trash and unavailable semantics.
- `PUT /library/sections/{id}/emptyTrash` (S1).
- An "empty trash automatically" setting.
- Mass-removal safeguards.

**Acceptance criteria**
1. A scan where a root is empty but previously had items, or where any
   walk error occurs under a root, does not remove items under the
   affected subtree. The section is marked partial or failed, and an
   admin-visible activity or log entry is produced.
2. Items whose files disappear are marked unavailable and keep their IDs,
   play state, collection membership, and playlist entries. If the file
   reappears at the same path, the item becomes available again with the
   same ID.
3. Unavailable items are removed only by `emptyTrash`, or by a per-server
   auto-empty preference whose default is off. The spec documents this
   with provenance S13 and S5.
4. Regression tests cover:
   - an empty mountpoint;
   - a `chmod 000` subdirectory;
   - a transient `ENOENT` mid-walk;
   - that collection, playlist, and play state survive.

### P1: correctness, security, and compatibility

#### F-02 · P1 · Defect: identities are tied to the file path and the library title

**Evidence**
- `internal/library/apply.go:80` and `:100`: item, media, and part IDs
  come from `a.prev[f.Path]`.
- `internal/library/store.go:274-305`: `SyncSections` matches sections by
  `type + title`. A section not in the config is deleted with all its
  items and collections (`:301-302`).
- `docs/spec/accounts.md:153-156` acknowledges that a re-added section gets
  a new ID.

**Impact.** Renaming a library's title in `sloplex.json` silently
destroys and rebuilds it. The effects are:

- a full rescan and re-probe;
- every account's history for it is lost;
- collections are lost;
- restricted accounts lose access.

Moving or renaming a single file, for example after a tool fixes a name,
loses its history.

**Missing.** Stable section identity, and some way to carry state across
moves: a content fingerprint, external IDs from `.nfo` `uniqueid`, or an
explicit migration.

**Acceptance**
1. Sections get an immutable ID or UUID that survives a title change. The
   config either supports an explicit `id`, or the library is managed
   through the API (F-13).
2. A file moved within a section keeps its item ID. One approach is to
   match removed and added files in the same scan by size, duration, and
   a partial hash. The heuristic is specified as **(sloplex)**.
3. Orphaned play-state, selection, and playlist entries are reported, and
   can be reattached or pruned.

#### F-03 · P1 · Defect: no durable writes, backups, or corruption recovery

**Evidence**
- `internal/atomicfile/atomicfile.go:11-33`: write to a temp file, then
  rename, with no `fsync` of the file or the directory. A repository-wide
  grep finds no `Sync()` call.
- Every play-state update rewrites the whole `playstate.json`
  (`internal/playstate/playstate.go:132-149`). The web app reports
  progress every 10 s (`docs/spec/web.md:61`).
- Every scan rewrites the whole `library.json` (`store.go:488-491`).
- An unparseable store is fatal at startup
  (`internal/library/store.go:217-223`; `cmd/sloplex/main.go:79-82`).
- There are no backups.

**Impact.**

- After a power loss, one of these JSON files may be empty or truncated.
  How likely this is depends on the filesystem; ZFS on TrueNAS is more
  forgiving than ext4 with `noauto_da_alloc`, but this is unverified.
- The server then refuses to start, and there is no backup to restore.
- Plex ships rotating database backups (S10).

**Acceptance**
1. Writes `fsync` the temp file and then the parent directory.
2. Rotating backups (for example N=3, as in S10) are made on a schedule,
   with a configurable backup directory and a documented restore.
3. On a parse failure, startup offers or uses the newest valid backup and
   logs loudly.
4. A load test of 10k items and 20 concurrent timeline reporters shows
   bounded write amplification. Batched or debounced play-state writes
   are an acceptable design.

#### F-04 · P1 · Security defect: `allowedNetworks` accepts public and all-address CIDRs and grants owner rights

**Evidence**
- `internal/config/config.go:199-209` parses any prefix.
- `internal/server/middleware.go:166-168` treats any peer in it as the
  **owner**.
- `docs/spec/auth.md:46-51`.

Plex documents, for the equivalent setting: "Public (WAN) addresses are
not valid for this server setting" and "Any app connecting ... will be
treated as the admin/owner" (S6, S12).

**Impact.** A typo such as `0.0.0.0/0`, or a public range on a
port-forwarded server, makes every internet client the owner. The owner
can manage accounts and TrueNAS one-click update settings (`requireOwner`
routes, `internal/server/updates.go:35-38`). The deployment guide does
warn against this (`docs/deploy-truenas.md:144`, `:346`); the code does
not enforce it.

**Acceptance**
1. Config validation rejects prefixes that contain globally routable
   addresses, and the default route, unless an explicit
   `allowPublicTrustedNetworks: true` is set. The rejection is logged.
2. A warning is logged at startup whenever `allowedNetworks` is non-empty.
3. Unit tests cover `0.0.0.0/0`, `::/0`, a public /24, RFC 1918, ULA, and
   CGNAT `100.64/10`. The spec states the Tailscale/CGNAT position.

#### F-09 · P1 · Clean-room evidence: provenance cannot be audited, and the official API document is unused

**Evidence.** Every compatibility-facing spec page cites "publicly
available community documentation ... and open-source client libraries'
public docs" with no URL, title, version, or retrieval date:

- `docs/spec/http-api.md:3-16`
- `playstate.md:3-14`
- `artwork.md:3-10`
- `search.md:3-9`
- `streams.md:3-11`
- `transcode.md:3-19`
- `collections.md:3-18`
- `playlists.md:3-14`
- `accounts.md:3-6`
- `discovery.md:3-8`

Plex published an official OpenAPI document on 2025-09-15 under
Apache-2.0 (S1, S2). The spec never mentions it.

**Impact.**

- A reviewer cannot check that each fact came from an allowed source.
  Rule 3 in `docs/spec/README.md:20-21` requires the source to be named.
- Where the spec differs from the official document (F-10), there is no
  way to tell whether the spec followed an older community source or
  guessed.
- Black-box observations (an allowed source) are never cited, so none
  appear to have been made.

**Acceptance**
1. Each wire fact (path, verb, parameter, attribute, enum, status) has a
   citation with URL, document version (for example "PMS API 1.2.3"), and
   retrieval date. A provenance table per page is enough.
2. Facts taken from S1 note its Apache-2.0 licence. If any schema text is
   reproduced, a NOTICE or attribution is added. A decision is recorded
   on whether reproducing S1 schemas is allowed under rule 2 of
   `docs/spec/README.md`; Apache-2.0 permits it with attribution.
3. Facts from black-box observation reference a fixture committed under
   `test/fixtures/<plex-version>/…`. The fixture records the server
   version, client, date, and redactions, plus a statement that the
   software was lawfully run.
4. A CI check fails if a spec page lacks a `## Provenance` section or has
   uncited bullets. A simple lint is enough.

#### F-13 · P1 · Missing: preferences API, runtime settings, and library management over the API

### P2: major gaps and lesser defects

#### F-05 · P2 · Defect: login throttling is per TCP peer, which behind the shipped Tailscale proxy is per-deployment

**Evidence.**

- The limiter is keyed by `remoteIP(r)`, which is `r.RemoteAddr`
  (`internal/server/accounts_api.go:177-183`, `:436-480`). Ten failures
  give a 15-minute lockout (`docs/spec/accounts.md:212-214`).
- In the shipped remote-access layout, every tailnet user arrives from the
  Tailscale container (`deploy/compose.tailscale.yaml`, the `Proxy:
  http://sloplex:32400` handler).

**Impact.**

- One user mistyping, or any tailnet peer guessing, locks every remote
  user out of logging in for 15 minutes.
- There is no per-account limit, so a guesser spread across many IPs on
  the LAN is not slowed.

**Acceptance.** Limit per account name as well as per peer. Optionally
trust a forwarded client IP only from a configured proxy address, and
spec it. Successful logins from other peers must not be blocked by one
peer's failures. Add tests for both cases.

#### F-06 · P2 · Defect: the non-revocable owner master token is written to logs

**Evidence**
- `cmd/sloplex/main.go:75-76` logs `token` on first start.
- `docs/spec/accounts.md:124-125`: owner master tokens "cannot be revoked
  through the API".
- The container logs go to json-file with rotation
  (`deploy/compose.yaml`), readable by anyone with Docker or TrueNAS
  app-log access.

**Acceptance.**

- Do not log the value. Log the file path that holds it instead.
- Add `sloplex -print-token` and `-rotate-token` CLI commands, with a
  documented rotation.
- Add a test that captures the log and asserts the token is absent.

#### F-07 · P2 · Missing: TLS and secure-connection settings

**Evidence.**

- `cmd/sloplex/main.go:198-207` only calls `ListenAndServe`.
- Tokens travel in query strings (`docs/spec/auth.md:15-17`;
  `docs/spec/web.md:29-30`).

S6 documents these settings:

- Secure connections: Required, Preferred, or Disabled;
- custom certificate location, passphrase, and domain (PKCS#12);
- strict TLS;
- IPv6.

`*.plex.direct` certificates are external-service-dependent (§3). Local
custom certificates are not.

**Acceptance.**

- An optional TLS listener with PEM or PKCS#12 certificate and key.
- Required/Preferred modes. Required rejects plain HTTP except loopback.
- A strict-TLS minimum version setting.
- Tests with a self-signed certificate.

#### F-08 · P3 · Partial: HLS session URLs remain usable after their token is revoked

**Evidence.** `docs/spec/auth.md:66-68`. This is documented and
intentional (bearer session ID).

**Acceptance.** Revoking a token, deleting an account, or changing a
password stops that principal's sessions, with a test.

#### F-15 · P2 · Partial: Plex movie naming conventions are not honoured

**Evidence.** I ran a throwaway probe, since deleted, of `ParseMovie` at
this commit:

| Input | Sloplex result | Plex documented behaviour (S14) |
|---|---|---|
| `Blade Runner (1982) {edition-Final Cut}.mkv` next to `Blade Runner (1982).mp4` | Both parse as `"Blade Runner" 1982`, so they become **versions of one item** (`docs/spec/http-api.md:371-372`) | Separate editions, each its own entry. S14 notes this needs Plex Pass |
| `{tmdb-272}` / `{imdb-tt0372784}` | Stripped from the title; the ID is discarded | Used to identify the movie |
| `Kill Bill (2003) - pt1.mkv` and `- pt2.mkv` | Same title, so two **versions**, each one-part (`apply.go:96-111` makes one Part per Media) | One item whose Media has **two Parts**, played in sequence. The suffixes are `cdX/discX/diskX/dvdX/partX/ptX` |

**Impact.**

- Split-file movies play only the first half. The second shows up as an
  alternative "version".
- Edition choice is reduced to an unlabeled version picker.

**Acceptance.**

- Recognise the S14 split suffixes and stack them into one Media with
  ordered Parts. Transcode and direct play must handle multi-part media,
  including the offset across parts.
- Parse `{edition-…}` into an `editionTitle`, kept as separate items or
  labeled versions, which is a spec decision.
- Keep `{imdb|tmdb|tvdb-…}` as external GUIDs (see F-17).
- Add parser tests for each S14 example.

### 5.4 Reliability and testing

- **Unit and HTTP tests.** There are 184 `Test*` functions; I counted
  them, not ran them. Coverage is broad for what exists: auth modes,
  restriction 404s, playlists, collections, transcode decisions, HLS
  subtitles, and throttling.
- **Gaps.**
  - No fault-injection tests for scans: empty root, EACCES, mid-walk
    errors (F-01).
  - No crash or durability tests (F-03).
  - No fuzzing of parsers that read untrusted input: `.nfo` XML, the
    subtitle converters, the ffprobe JSON, and the filename parsers. Go's
    native fuzzing would fit.
  - No load or scale tests (F-28).
  - No conformance or contract tests (F-10, F-11).
- **E2E.** Four Playwright suites run against Sloplex's own web app,
  using a custom harness (`test/e2e/lib.mjs`). They are valuable for the
  app; they say nothing about Plex-client compatibility.
- **CI.** gofmt, vet, `-race` tests, build, e2e, a container build, and
  the smoke test, including the Tailscale variant. It is solid. See
  F-29 for pinning.

## 7. Notes on what is good

These are worth keeping as the project grows:

- Every spec page has a Provenance section, and **(sloplex)** choices are
  marked consistently.
- Restricted items return 404, indistinguishable from missing ones
  (`accounts.md:147-150`).
- Password storage is PBKDF2 with 600k iterations, tokens are stored only
  as hashes, and master tokens are compared in constant time.
- The web app ships a strict CSP, and `Referrer-Policy: no-referrer`
  protects tokens in media URLs.
- `/photo/:/transcode` never fetches remote URLs.
- The transcoder is unusually well engineered and documented:
  - pipeline fallback;
  - a benchmark-driven preset choice;
  - throttling;
  - HDR tone mapping verified by a luminance check;
  - honest "Not implemented yet" and measurement caveats.
- Container hardening: read-only root filesystem, all capabilities
  dropped, no new privileges, and digest-pinned base images, all
  smoke-tested.

## 8. Limitations of this review

1. **No target version or platform was given.** I used the official API
   document's floor (PMS 1.43.4, API 1.2.3) as the reference. Plex
   behaviour before and after that version, and across platforms, was not
   considered.
2. **No client matrix.** Every compatibility statement is about the wire
   shapes in S1. None is about what any client actually sends.
3. **No black-box fixtures.** I captured no Plex traffic. Where S1 is
   silent or incomplete (S2), Plex behaviour is unknown to this review.
   Examples: the `stop`/`ping` transcoder endpoints, and the
   client-profile header grammar.
4. **Settings inventory is partial.**
   - Read: General, Library, Network, Transcoder, Bandwidth, Remote
     Access, Scheduled Tasks, DLNA, Languages, Authentication, Trash,
     Movie naming.
   - Not read: Agents, Plugins, Extras, Optimized Versions, Live TV & DVR
     setup, Troubleshooting, the advanced hidden settings list (S16), the
     music, photo, and TV naming pages, local media assets, Plex
     Home/managed users, sharing restrictions, Downloads.
   - Findings that touch these areas rest on the existence of S1
     operation groups or the S3 category list, and are labeled that way.
   - *Round 2:* §9 read all of these except Plugins and a photo-naming
     page; I found no official photo-naming article. §9.6 lists what is
     still unverifiable.
5. **S1 was read mechanically.** I extracted paths, verbs, parameters,
   and enums by script. I did not review every response schema in depth,
   so attribute-level element conformance (for example every `Metadata`
   attribute) is not assessed.
6. **Static review.** Most findings come from reading the code. Only the
   F-15 parser behaviour was executed. F-01 and F-03 failure modes are
   reasoned from the code, not reproduced. I did not run the full test
   suite, which the parent runs.
7. **Not a security audit.** The security findings are the ones I noticed
   while checking parity. There was no systematic threat model or
   penetration test.
8. **No parity certification.** Even with every finding fixed, parity
   would still need M2's target matrix and contract fixtures to be shown.

### 9.4 Additional findings

#### F-31 · P2 · Partial: local media assets cover only part of the documented names

**Evidence.** §9.3 rows marked F-31.

- `default` posters and `.tbn` files are ignored.
- Numbered alternates are invisible.
- Clear logos and square art are never discovered.
- `.smi` subtitles and `subs`/`subtitles` folders are ignored.

S25 and S26 document all of these. The subtitle folder needs PMS 1.41.0
or later, per S26.

**Impact.** A library that is laid out correctly for Plex loses its
posters, logos, and subtitles silently. No error is shown.

**Acceptance.**

- Extend `findArtwork` and `parseSidecar` to S25/S26, with one test per
  documented example.
- Decide in `artwork.md` whether alternates are exposed, and how. That is
  a spec decision.
- Emit a clear-logo attribute only after its name is confirmed against
  S1 or a fixture.

S1 v1.2.3 has no per-item poster or art selection operation; I found
only `GET /library/sections/{sectionId}/arts`. Exposing alternates
therefore needs either a cited source or a **(sloplex)** design.

#### F-32 · P2 · Partial: TV naming misses multi-episode ranges, folder IDs, and `.plexmatch`

**Evidence.** `docs/spec/http-api.md:382-383`, and §9.3.

**Impact.**

- A double episode appears as one episode. The second number is missing
  from season lists, On Deck, and the watched count.
- Users who rely on S23's ID tags or a `.plexmatch` file get title-based
  grouping instead.

**Acceptance.**

- Multi-episode files populate every episode in the range, sharing one
  Part. S23 says they "play the whole file".
- Keep folder ID tags as GUIDs (with F-17).
- Specify a local subset of `.plexmatch`, or a documented divergence.
  S23 names the file but does not give its grammar; finding a public
  source for that grammar is part of this work.

#### F-33 · P3 · Partial / unverified: extras folder names are skipped at any depth

**Evidence.** `internal/library/scanner.go:162` applies `skipDir` to
every directory below the root. The list includes generic names: `Other`,
`Shorts`, `Scenes`, `Extras`, `Interviews` (`parse.go:111-115`). S24
describes these folders only *inside a movie's folder*.

**Impact.** Some ordinary layouts are silently not indexed:

- a movie library `Movies/Shorts/<film> (2010)/…`;
- a grouping folder `Movies/Other/…`;
- a show folder named exactly `Extras` or `Other`.

Combined with F-01, renaming an existing folder to one of these names
removes its items.

**Acceptance.** Treat the names as extras only directly inside an item
folder (a movie folder, or a show or season folder), and test each case.

Plex's own behaviour for these names at other depths is **not
documented**. Do not claim parity either way without a fixture.

#### F-34 · P2 · Missing: rating and label restrictions, and labels as data

**Evidence.** §9.2, "Library access" rows. Access is per section only.
`contentRating` exists on items but is never used for access. Labels
have no field in the store.

**Impact.**

- No parental control is possible within a library.
- Labels block three things: S30 restrictions, the S1 tag and filter
  surfaces, and the metadata editing in F-17.

**Acceptance.**

- Labels in the item model, editable by admins.
- Per-account allow and exclude lists for ratings and labels, enforced
  with the existing 404 indistinguishability (`docs/spec/accounts.md`).
- Optional preset profiles, marked **(sloplex)** unless their rating
  lists are cited to S30.
- Restricted accounts must not reach items through search, hubs,
  collections, playlists, or parts URLs. Tests must cover each path.

#### F-35 · P3 · Missing: movie pre-roll and local cinema trailers

**Evidence.** S19 settings, and S1 `POST /playQueues` `extrasPrefixCount`.
Sloplex has no play queues (F-12) and skips trailers at scan time (F-16).

**Impact.** A documented, fully local feature is absent: pre-roll by
path, and trailers drawn from the user's own library. It needs no
plex.tv.

**Acceptance.**

- An admin setting for pre-roll paths, with S19's `,` (play all in
  order) and `;` (pick one) semantics.
- Paths are validated as admin-only server files.
- Play-queue creation honours `extrasPrefixCount`, per its S1
  description, and leaves prefixes out on resume.
- Depends on M5 (play queues) and F-16 (extras).
